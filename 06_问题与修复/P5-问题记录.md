# P5 问题与修复（2026-11-19）

## 已修复：1 个（本轮最有价值的 bug）

### 1. 监控跑 unittest 会删库，提案记录一起被删（已修复）
- 现象：首次手动走完整六步时，部署、监控都 healthy，但 improve-rollback 返回 not_found，提案记录查不到。
- 根因：monitor() 里跑了 P1 的 unittest 注入测试，那个测试的 fresh_db() 会删 data/jarvis.db；而提案、评价、部署三张表当时也存在 jarvis.db 里，一起被删了。监控本身没报错，是测试的副作用把治理记录删了。
- 修复（两处）：
  1. 提案、评价、部署三张表改存独立的 data/improvements.db，不与 jarvis.db 共库。治理记录与业务数据分离，业务测试再怎么清库也删不掉治理记录。
  2. monitor() 不再跑 unittest，改用直接调用 WriteGate 的探针（boot + health + gate 探针），不碰数据库。
- 回归：修复后手动六步全通，38 项测试全通过；测试 1 里监控后回滚正常。
- 教训：测试的清理逻辑（fresh_db）是“删整个库”，任何与业务同库的记录都会被它误伤。治理类记录必须独立建库；监控类操作必须用无副作用的探针，不能复用会清库的测试。

## 设计决策：1 个

### 2. 测试只跑 boot + P1 记忆测试，不跑全量 38 项（已定案）
- 现状：improve-test() 在临时复制目录里跑 boot + P1 的 2 项测试（注入拦截、100 对话），约 11 秒。
- 理由：全量 38 项约 81 秒，提案测试每次都跑全量太慢；P1 的 2 项是记忆治理的核心回归门，改动影响最大的就是记忆层。改 router/gateway/planner 的提案，P1 测试覆盖不到，但 boot 能发现 import 与启动错误。
- 后续：接真实供应商后，提案测试要按目标文件选回归门（改 router 跑 P2 测试，改 gateway 跑 P3 测试，改 planner 跑 P4 测试）。
- 状态：已定案，写入 improvement.py 的 docstring 之外，此处留档。
