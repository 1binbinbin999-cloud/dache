# P2 问题与修复（2026-11-19）

## 已修复：1 个

### 1. import_jsonl 的 imported 计数用 total_changes 累计值判断（已修复）
- 现象：初版代码用 `if conn.total_changes > 0` 判断每行是否导入成功。total_changes 是累计值，第一行导入成功后它就一直 >0，后续被 INSERT OR IGNORE 跳过的行也会被误计为 imported。
- 修复：每行执行前记录 `before = conn.total_changes`，执行后比较 `conn.total_changes > before`。
- 回归：测试 7 里重复导入 imported=0，验证了修复。
- 教训：SQLite 的 total_changes 是连接级累计值，不能当“本次执行是否生效”用；P1 的教训（先写最小调用测试）在这里没完全落实，import 是先写完才测的，下次先写测试再写实现。

## 设计修正：1 个（不是 bug，是发现的原则问题）

### 2. logical=local 的切换链最初会回落到云端（已修正）
- 现象：初版 chain_for 对所有逻辑模型都是“首选 → capable → local”。logical=local 时链是 [stub-local, stub-capable]，本地失败会悄悄回落到云端。
- 问题：这会打破“本地”承诺——用户明确要本地时，系统不该在用户不知情的情况下把问题发给云端模型。
- 修正：logical=local 时只走 [stub-local]，不回落；全失败时走本地规则降级。
- 后续：接真实供应商时同样适用：local 映射到本地 Ollama 模型，失败只降级，不上云。

## 已知限制

### 3. Stub 的 token 是按词数算的近似值，不是真实分词结果
- 现象：tokens_in = prompt.split() 的词数，中文无空格文本会算成 1 个 token；tokens_out 同理。
- 后续：接真实 API 时用供应商返回的真实 usage；本地模型用 tokenizer 算。Stub 阶段只用于验证“审计字段存在且 hash 一致”，不用于成本核算。
- 状态：已知限制，不阻塞 P2。

### 4. --fail 是测试用的模拟失败，不是真实超时/5xx
- 现象：故障切换用 `--fail` 参数模拟供应商失败，证明的是“Router 收到 ProviderError 时会切换”，不是“真实网络超时时一定能切换”。
- 后续：接真实供应商后，要做一次真实失败演练（拔掉 Key、断掉代理），验证超时时间与切换行为。
- 状态：已知限制，留 P3 工具网关 / 真实供应商接入时验证。
