# Jarvis 用户需求基线（V1.1，2026-11-19）

> 用途：这是判断开发有没有跑偏的依据。分类必须严格，不能把 Muse 的建议擅自当作用户已确认的需求。
> 来源：用户 2026-11-19 的第一阶段完整 brief、V1.1 培养指令、此前导入的长期记忆、已交付的《Jarvis 技术可行性验证报告》。

## 分类说明

- **A. 用户明确提出的要求**：用户原话或明确书面要求，开发必须满足。
- **B. 已经确认的技术方案**：用户已明确确认的设计方向，不是 Muse 的建议。
- **C. Muse 自己提出的建议**：来自可行性报告或本基线整理，尚未经用户确认，不得当作已确认需求。
- **D. 尚未验证的假设**：报告或调研中的推断，需原型实测才能确认。
- **E. 需要用户决定的问题**：集中列出，不在开发中擅自决定。

## A. 用户明确提出的要求

### A1. 最终目标：真正属于自己的独立个人 AI 系统，名 Jarvis
- 不是普通聊天机器人，不是简单 AI 助手，不是多个现成 AI 产品的组合。
- 逐渐成长为拥有独立核心、长期记忆、知识体系、用户理解、行为决策、工具使用、持续学习能力的个人智能系统。
- 11 项最终目标：理解用户；理解用户所处环境和情境；记住过去；积累知识和实践经验；主动发现问题和机会；独立研究、分析和验证信息；制定方案并评估不同选择；在授权范围内执行任务；检查执行结果；根据结果修正认知和能力；随长期使用逐渐成长。
- 不应永远只是等待提问的工具，应逐渐具备主动工作能力。

### A2. 最高优先级：真正独立
- 核心系统独立于外部 AI 服务。GPT、Muse、Gemini、DeepSeek、Qwen 等只能是外部能力供应商，可调用、可同时调用多个，但不能依赖任何一个才能存在。
- 必须实现 10 项独立：核心架构、记忆系统、知识系统、用户模型、行为与决策模型、工具管理、权限管理、数据存储独立，模型接口可替换，外部 AI 可随时更换或停止。
- 极端验收：假设 GPT、Muse、Gemini 等全部停止，Jarvis 仍能启动，读自己的记忆和知识，运行本地程序，执行不依赖外部服务的任务。高级推理可暂时失效，自身不能瘫痪。
- 必须区分：独立运行、独立推理、独立学习、独立执行，四者不是一回事。

### A3. 核心能力（8 项）
1. 长期记忆：持续记录管理对话、观点判断、行为选择、长期目标、项目进度、经验反馈、过去错误和修正、不同阶段变化；不只是存聊天记录，要研究提取、分类、去重、关联、检索、更新、纠错，区分事实、用户观点、推断、待验证信息。
2. 知识系统：自主获取外部信息、阅读分析文档、整理知识、建立关联、保存来源、检查过时、交叉验证、按新证据更新旧知识；知识库与用户记忆必须分开。
3. 用户理解：动态用户模型，覆盖思考方式、判断习惯、决策方式、行为模式、长期目标、关注领域、表达习惯、认知变化；不能只按单次对话贴标签；历史判断允许被新证据修正或推翻。
4. 自主研究与验证：发现问题 → 提出假设 → 收集资料 → 交叉验证 → 形成结论 → 保存证据；区分事实、猜想、推断、已验证结论。
5. 多 AI 协作：把问题交给不同模型、比较答案、互相检查、识别分歧、独立核验重要结论、按任务选模型；信息组织、记忆、任务管理、决策流程必须由 Jarvis 自己控制。
6. 主动工作：监控授权信息源、发现异常变化、识别可能问题、发现与目标相关的机会、主动建议、在授权内执行、报告结果。
7. 工具使用：用电脑、文件、浏览器、软件接口和其他授权工具；独立权限控制；AI 认为有必要不自动获得执行权限。
8. 自我改进：检查运行状态、发现程序错误、分析性能瓶颈、提出代码优化、编写改进版、隔离测试、比较前后、获授权后部署；流程必须是 Proposal → Test → Evaluation → Approval → Deploy → Monitor；禁止未经授权直接改核心规则、权限系统、安全边界。

### A4. 部署路线
- 先验证 → 再开发 → 再测试 → 最后迁移到实体电脑。
- 当前云端虚拟电脑只为降低前期成本；当前不买实体硬件、不正式开发（V1.0 时）、不提前订阅不必要收费服务。
- 未来最终运行环境是用户自己控制的实体电脑；云端成果必须能迁移，不能绑定 Muse 专属环境。
- 必须考虑：源码、配置、数据库完整导出；长期记忆、知识库完整迁移；模型及依赖管理；自动化部署；备份恢复；本地独立运行；外部服务替换。
- 未来可能买大容量存储设备，具体容量、类型、性能暂不确定，按实际架构和测试结果决定。

### A5. 执行纪律（V1.0，继续有效）
- 不把推测当已验证事实；重要结论提供依据和来源。
- 需求本身有技术矛盾时必须主动指出；不要为漂亮报告掩盖技术限制；未经用户确认不改变项目目标。
- 低成本、可丢弃的技术验证允许，但须提前说明目的，不得演变为正式开发（V1.0 时）。

### A6. V1.1 新增要求
- 通过持续实际开发、模拟部署、测试、故障排查、经验总结，培养 Muse 为总工程师。
- 采用小步迭代，每轮明确：本轮目标、技术方案、实际交付、运行测试结果、存在的问题、验收标准、下一步计划。
- 不允许只提交设计报告而不实际开发；不允许为展示进度一次性写大量无法验证的代码。
- 每轮结束必须把经验写入工程档案（本 Jarvis/ 目录），重要经验写入可导出文件，不能只留聊天记录。
- 云端测试通过不等于实体电脑测试通过，更不能用云端证明未来本地大模型性能；最终必须在独立环境验证迁移、安装、数据恢复和运行。
- 成本：未经批准不得产生新付费项目；API 总预算上限 30 美元；单项测试预算不超过 5 美元；不得擅自购买硬件或服务；不得擅自修改核心规则、安全边界和系统权限；重要修改必须有备份和回滚方案。
  - 修正（2026-11-19 20:43，用户决定）：第二阶段总预算调整为 **0 美元**，单项测试上限改为 0 美元。第一阶段实际花费 $0 不变；原 $30 上限为第一阶段计划值，不再适用于第二阶段。见 ADR-010。

## B. 已经确认的技术方案

以下由用户在 V1.0 brief 中明确确认，是已确定的设计方向，不是 Muse 建议：

- 13 个模块：Agent Core、Model Router、Memory、Knowledge、User Model、Behavior Model、Planner、Tool Gateway、Permission/Policy、Audit、Evaluation、Proactive Engine、Learning Engine。
- 核心闭环：Situation → Context → Options → Decision → Action → Outcome → Result → Evaluation → Learning。
- 自我改进流程：Proposal → Test → Evaluation → Approval → Deploy → Monitor。
- 部署路线：先验证 → 再开发 → 再测试 → 最后迁移到实体电脑（见 A4）。
- Local First、Cloud Optional；模型可替换、数据自主控制、记忆持续积累、权限边界明确（来自长期记忆导入，用户已确认）。
- 工程档案目录结构：00_项目总纲 / 01_用户需求 / 02_总体架构 / 03_技术决策 / 04_源代码 / 05_测试记录 / 06_问题与修复 / 07_开发经验 / 08_部署手册 / 09_版本记录 / 10_交接与迁移（V1.1 用户建议建立）。

**注意：** 以上只确认了“方向和模块名”，每个模块的具体技术方案尚未确认，须由实际开发验证。

## C. Muse 自己提出的建议（尚未经用户确认，不得当作已确认需求）

来自《Jarvis 技术可行性验证报告》及调研，状态均为“建议，待用户确认或原型验证”：

1. 推荐总体架构：确定性核心（无模型依赖）+ LangGraph 编排 + LiteLLM 自托管路由 + Ollama/llama.cpp 本地兜底 + Postgres+pgvector 唯一事实库 + MCP Tool Gateway + OPA/代码层权限 + 审计。
2. 架构两处修正：新增事件日志为唯一事实源，防记忆污染；Behavior Model 不单独立库，改为 Planner 内策略层，防数据漂移。
3. 技术选型：LangGraph、LiteLLM、Ollama、llama.cpp、Postgres+pgvector、Mem0 只做提取适配器、Docling 解析、BGE-m3 本地 embedding、Hybrid 检索 + 本地 reranker、Docker/Podman。
4. 推荐路线：本地核心 + 云端模型（方案 C）为现阶段最合理路线。
5. 最小验证原型 P0–P5（见第一阶段开发计划）：离线启动、路由切换、工具网关、Planner、自我改进、记忆治理。
6. 成本四档：零付费 / 低成本 / 中等 / 高性能，及 API 按任务路由（日常便宜模型，重要结论旗舰复核）。
7. 记忆与知识设计：Postgres 唯一事实库，事实表带 id/type/claim/confidence/evidence_grade/source/valid_from/valid_until/status/superseded_by；写时 gate、版本化、不删除旧版。
8. 权限分级：L0 自动 / L1 确认 / L2 审批 / L3 禁止；沙箱 Docker + cap-drop + 只读根文件系统 + 默认拒绝出站。

**用户尚未对以上任何一条说“确认采用”。** 第一阶段开发计划中的 P0 只验证其中最基础的部分，不等于全盘采纳。

## D. 尚未验证的假设

1. 本地小模型（7–14B）在 Jarvis 具体任务（记忆提取、规划、工具调用）上的准确率，没有现成基准可直接套用，需自有评测集实测。
2. 记忆提取准确率、去重、纠错、证据等级在长期真实使用中是否可靠，无法靠一次开发证明，需长期运行 + 人工抽查。
3. 跨源交叉验证能否真正发现错误，而非多个来源互相抄写，需实测。
4. LiteLLM、LangGraph、Mem0 等开源项目的版本、许可、安全事件后续变化，需在采用前复查官方文档。
5. API 价格、硬件价格（尤其 2026-11-19 存储暴涨期）变化极快，报告中的价格只在查询日有效，下单时必须重核。
6. 云端虚拟电脑的性能、后台运行限制、额度，不能外推到实体电脑。

## 矛盾与不明确之处（主动提出）

1. **“高级推理可暂时失效，但系统不能瘫痪” vs “主动研究、独立验证”**：停服期间 Jarvis 可继续值班、检索、执行既定规则，但主动提出的新判断可信度会下降。报告的解决办法：每条结论打「生成时所用模型 + 证据等级」标签，停服期产生的内容恢复后必须复核。—— 此为 Muse 建议，待用户确认。
2. **“核心独立” vs “第一版用 LangGraph/LiteLLM 等框架”**：框架是编排器和网关，不是核心本身；记忆、权限、审计、用户模型必须掌握在 Jarvis 自己的代码里，不能交给框架的托管服务。P0 会用代码边界证明这一点，而不是只靠声明。
3. **“记忆提取用 LLM” vs “外部 AI 全停后记忆写入要保留”**：写入流程保留，但提取改用本地小模型，需降置信度、打「待复核」标记。质量下降是诚实降级，不是等价替代。
