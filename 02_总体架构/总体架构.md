# Jarvis 总体架构（建议版，待原型验证，2026-11-19）

> 状态：C 类建议，未经用户确认采用。P0–P3 将逐项验证，验证失败就改架构，不硬撑。
> 依据：《Jarvis 技术可行性验证报告》第 3 节，5 路调研汇总。

## 原则（建议）

一句话：**模型只提议，代码才执行；模型只读快照，写入必须经过 Core / Gateway / 审批。**

## 分层结构（文字架构图，建议）

```
交互层：用户 / 聊天 / 定时任务 / Webhook / 文件变化
  只发事件，不直接调工具、不直接写记忆
        ↓ 事件 / 指令
Agent Core：确定性编排器（心脏，必须能离线启动）
  状态机 + 事件日志 + 检查点；拥有闭环
  Situation→Context→Options→Decision→Action→Outcome→Result→Evaluation→Learning
  唯一有权：组装上下文、调用 Planner、调用 Model Router、提交 Tool Gateway、写入 Memory/Knowledge、生成学习提案
    ↓        ↓        ↓        ↓        ↓
  Planner  Model    Tool     Memory/  Evaluation
  （计划）  Router   Gateway  Knowledge /Proactive
            （模型）  （工具）  UserModel /Learning
                      +Policy +Audit
```

## 模块职责（建议）

| 模块 | 职责 | 技术形态（建议） |
|---|---|---|
| Agent Core | 任务协调、状态机、事件日志、超时/重试/幂等、闭环驱动 | Python 确定性代码，不导入任何模型 SDK |
| Model Router | 统一 /v1/chat/completions 调用、模型选择、降级、预算、限流 | 直接适配器（已验证，S2-1/S2-2）；LiteLLM Proxy 为后续扩展选项，待用户决定；逻辑模型名 fast/capable/reasoning/local/embedding |
| Memory | 长期记忆：提取、分类、去重、关联、检索、更新、纠错，带来源与可信度 | Postgres+pgvector（后期）；P0 用 SQLite+文件，schema 同构，可迁移 |
| Knowledge | 知识获取、存储、检索、过期检查、交叉验证，与 Memory 分离 | RAG Hybrid：向量+全文检索 → 本地 reranker → top-5 |
| User Model | 动态用户模型：思考/判断/决策习惯、目标、变化史，可被新证据修正 | 版本化事实表，非单次标签；分 UserFacts / UserInferred / UserProfile 三层 |
| Behavior Model | 决策策略：选项评分、风险阈值、何时问人、何时自动做 | 建议改为 Planner 内策略层（报告修正 2），不单独立库，防数据漂移 |
| Planner | 任务分解为 DAG、依赖、验收标准、重规划 | Plan-and-Execute 为主，局部 ReAct；硬限制：无校验器连续步骤 <5 步 |
| Tool Gateway | 唯一工具入口：发现、校验、授权、执行、返回观察 | MCP Host/Client；工具能力卡：名、参数 Schema、读/写、额度、调用者 |
| Permission/Policy | 策略表：谁、哪个工具、什么参数、是否需审批、额度上限 | 代码表 + 审批表；OPA 为候选，P0 先用代码表，验证后再定 |
| Audit | 追加写、不可改的操作日志，与业务数据分离 | JSONL 追加日志 + 事件日志为唯一事实源（报告修正 1） |
| Evaluation | 结果验收：规则校验、测试、对照、人工抽查 | 冻结评估集 + 独立校验器，系统自己不能改评估器 |
| Proactive Engine | 定时、心跳、事件触发、阈值告警、机会发现 | Cron + 事件 + 心跳 15–60 分钟；静默阈值 + 去重，先规则触发再模型判断 |
| Learning Engine | 只产提案，不直接改系统；提案进队列待审批 | Proposal → Test → Evaluation → Approval → Deploy → Monitor |

## 调用链（允许 / 禁止，建议）

允许：
```
用户/事件 → Agent Core → Planner → Model Router → 模型提议
模型提议 → Agent Core → Permission/Policy 检查 → Tool Gateway → MCP Server/本地工具
工具返回 → Tool Gateway（标记为不可信观察）→ Agent Core → Evaluation → Memory/Knowledge（经 Core 写入）
```

禁止（架构红线，违反即失去独立性）：
- 模型 / Model Router 不得直接调工具、直接写 Memory/Knowledge/User Model、直接改 Policy/Audit/代码。
- Planner 不得直接调工具，只能产出计划给 Core 执行。
- 工具 / MCP Server 不得直接读 Core 状态、直接写数据库、直接调其他工具。
- Memory / Knowledge 不得被工具输出直接写入；必须经来源标注、隔离、Core 校验。
- Learning Engine 不得直接改代码、配置、权限；只能产出 Proposal。
- Proactive Engine 不得直接执行高风险动作；只能产出候选任务给 Core + 审批。

## 数据流（一次任务，建议）

1. Situation：事件/用户指令 + 时间、设备、当前目标快照。
2. Context：Core 从 Memory/Knowledge/User Model 只读组装“最小必要上下文”，带来源 ID，不把整库塞给模型。
3. Options：Planner 生成 2–3 个选项 + 各自成本/风险/验收标准。
4. Decision：Behavior 策略 + Policy 选一个；高风险进审批队列，暂停。
5. Action：Gateway 按 allowlist、参数 Schema、幂等键执行。
6. Outcome/Result：工具观察 + Evaluation 校验是否达到验收标准。
7. Learning：成功/失败经验写成提案，不直接改模型或规则。

## 持久化与迁移、可回滚（建议）

- 状态分三类：`config/`（YAML）、`data/`（SQLite/Postgres 导出为 SQL）、`memory/knowledge/`（Markdown + JSON，带来源）。
- 代码、配置、记忆、知识全部进 Git，禁止 force-push 到主分支。
- 每次部署打 Tag + 镜像 Tag；回滚 = 切回上一个 Tag + 恢复对应数据快照，禁止只回滚代码不回滚数据。
- 云端 → 实体电脑迁移 = 导出代码 + 配置 + 数据库 + 记忆/知识 + 模型清单（不是模型权重本身），在实体机上重建后导入。

## 降级设计（外部 AI 全停，建议）

```
L3 云端增强层（可丢）：GPT / Muse / Gemini / DeepSeek / Qwen 经直接适配器（已验证，S2-1/S2-2）+ 联网搜索 + 云端 SaaS；LiteLLM Proxy 为后续扩展选项
L2 规则/检索层（本地）：关键词+向量检索、模板回答、确定性规划图（无 LLM 节点也可跑）
L1 本地模型层（本地）：Ollama / llama.cpp + 本地小模型 + 本地嵌入 bge-m3 + 本地重排
L0 硬核（绝不依赖模型）：Python 核心、SQLite/Postgres、配置、策略、审计日志、调度器、Tool Gateway（allowlist）
```
- 启动路径不得调用 LLM；配置、数据库、权限、审计先启动，模型后加载。
- 所有云端调用走直接适配器（已验证，S2-1/S2-2），带预算、超时、重试上限；无 Key 时直接走降级，不报错瘫痪。（LiteLLM Proxy 为后续扩展选项，待用户决定）
- 降级矩阵见可行性报告第 2 节：启动/读记忆/读知识/本地工具完全保留；复杂推理/联网研究降级或丢失。
