# Muse 开发经验档案（第一阶段，2026-11-19）

> 规则：本文件只收录已经写入工程档案、有测试或决策记录佐证的经验。对话里说过但没落地的，不算固化，见第 5 节“未固化清单”。

## 1. 本阶段对用户需求的理解

### 1.1 用户真正要的是什么
- 不是一个聊天机器人，而是一个**属于用户自己的、能独立运行的个人 AI 系统**：核心、记忆、知识、用户模型、权限都独立，外部模型只是可替换的供应商。
- 验收标准是极端条件：外部 AI 全停时，Jarvis 仍能启动、读自己的记忆和知识、跑本地程序、执行不依赖外部服务的任务。
- 用户对“独立”的要求高于对“聪明”的要求：P0 先证明离线启动，而不是先接最强的模型，这个顺序就是用户需求的体现。

### 1.2 用户的工作方式
- 结论优先：先给结论，再按复杂度给必要解释；简单问题直接答，复杂问题充分推演。
- 证据分级：事实、观点、观察、推断、假设、待核实要分开说；不确定就说不确定。
- 独立判断：AI 要保持独立判断，不迎合；发现逻辑错误直接指出；真相与逻辑比面子重要。
- 小步迭代、每轮确认：每轮开发目标、技术方案、交付、测试结果、问题、验收标准、下一步计划，七项齐全才算一轮；不一次写大量无法验证的代码。
- 重要修改必须有备份与回滚方案；未经批准不产生付费、不改核心规则与安全边界。

### 1.3 需求基线的分类（已写入 `01_用户需求/用户需求基线.md`）
- A 类用户明确要求、B 类已确认技术方案、C 类 Muse 自己的建议（不等于用户确认）、D 类未验证假设、E 类待用户决策的问题。C 类不得擅自当作用户已确认的需求——这是本阶段反复用到的纪律。

## 2. 本阶段对 Jarvis 架构的理解

### 2.1 一句话架构
**模型只提议，代码才执行；模型只读快照，写入必须经过 Core / Gateway / 审批。**

### 2.2 六个已验证的架构判断
1. **确定性核心先行**：Agent Core 是纯确定性代码，不 import 模型 SDK，启动顺序写死在代码里。P0 证明了它。
2. **事件日志是唯一事实源**：JSONL 追加写，重启不丢；记忆、任务、审计都以此为底。P0 测试 3 验证。
3. **记忆治理先于记忆规模**：100 条合成对话的提取不难，难的是写错了怎么办。P1 的 gate、隔离区、Correction 记录、过期标记，就是“写错了能改、改了有历史”的机制。
4. **模型可替换 = 映射在配置里**：业务代码只认逻辑名，换模型只改 config。P2 测试 1 验证。
5. **权限检查在执行前**：拒绝的调用不执行，只记审计；拒绝的证明不是返回值，而是“数据库还在”。P3 测试 2 验证。
6. **改进必须走流程**：提案→测试→评价→批准→部署→监控，六步缺一不可；批准是用户的显式动作。P5 测试 1–4 验证。

### 2.3 两处架构修正（可行性报告之后）
- 修正 1：事件日志作为唯一事实源，防止记忆污染（报告原建议的记忆直写有污染风险）。
- 修正 2：Behavior Model 不单独立库，改为 Planner 内的策略层，防止数据漂移。

| E-03 | P2 local 切换链最初会回落云端 | 写完 chain_for 后自问：用户明确要本地时，系统能不能悄悄上云？ | local 只走本地，失败走规则降级 | P2-问题记录、JIS-009 |

## 4. 有效方法（已验证，可迁移）

| 方法 | 内容 | 适用场景 |
|---|---|---|
| M-01 每轮一个完整可运行目录 | 复制上一轮目录再改，上一轮原样保留为回滚点 | 任何多轮迭代开发 |
| M-02 先证明流程，再谈质量 | P1 先用规则模板提取，不调 LLM；P2 先用 Stub，不接真实 API | 新能力接入时，隔离“流程 bug”与“模型/供应商行为” |
| M-03 拒绝的证明是副作用缺席 | 权限测试不断言返回值，而断言“数据库还在”“第三步没执行” | 权限、审批类测试 |
| M-04 失败分支先写 | Planner 先写 denied/failed 的停表逻辑，再写 done 的记录 | 规划器、审批流等“失败时不乱走比成功时跑得快更重要”的模块 |
| M-05 外部依赖先验证再写代码 | P3 写 sandbox.py 前先在命令行验证 unshare 可用、探针返回 101 | 沙箱、网络、硬件等环境依赖 |
| M-06 测试的清理逻辑要隔离治理记录 | 治理类记录独立建库；监控用无副作用探针 | 任何“测试会清库”的项目 |
| M-07 权限边界按最保守的解释写 | 涉及隐私/安全的默认行为，选最保守的，不选最方便的 | local 链、审计脱敏、不可变规则 |
| M-08 诚实分级 | 测试分真实验证/模拟验证/尚未验证；模拟测试不描述为真实环境验证 | 测试报告、阶段总结 |
| M-09 每轮七项齐全 | 目标、方案、交付、测试结果、问题、验收标准、下一步计划 | 每轮开发 |
| M-10 待定项当轮定，不拖 | P3 的审计脱敏与 actor 待定项在 P4 开头就定案 | 跨轮遗留管理 |
| M-11 边界原则：当轮可定则定，不擅自定 | 当轮能够依据现有证据和用户授权确定的事项，应当当轮定案；涉及用户选择、费用、安全边界或外部条件的事项，不得为了消除待定状态而擅自决定 | 任何待定项的定案决策 |
