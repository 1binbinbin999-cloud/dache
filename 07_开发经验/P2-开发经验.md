# P2 开发经验（2026-11-19）

## 成功的方案及原因
1. **Stub 优先，不接真实 API**：全部 18 项测试用 Stub 跑完，费用 $0。成功原因：路由逻辑（映射、切换、降级、审计）与供应商无关，先证明逻辑成立，再接真实供应商；如果先接真实 API，网络、Key、计费、供应商行为会和路由 bug 混在一起。
2. **映射只在 config.yaml，业务代码只认逻辑名**：测试 1 证明只改配置就能换模型。成功原因：这是 Jarvis“模型可替换”的核心，P2 就把它钉死，后面接 LiteLLM 时映射层不用改。
3. **每家最多试一次，attempted 列表写进审计**：测试 2、3 的 attempted 字段直接证明了不死循环。成功原因：切换逻辑的正确性不能靠“没卡住”来证明，要靠可查的尝试记录。
4. **P1 遗留（回滚、导入）在 P2 顺手补上**：测试 6、7 通过。成功原因：遗留项越拖越难补，趁 P2 改 memory.py 时一起做，改动面小。

## 失败的方案及原因
1. **import 计数用 total_changes 累计值**：重复导入会被误计。失败原因：没理解 SQLite total_changes 是连接级累计值。已修复，教训：先写测试再写实现，这次没完全做到。
2. **local 切换链最初会回落云端**：不是代码 bug，是设计原则问题。发现原因：写完 chain_for 后按“用户明确要本地时系统能不能悄悄上云”自问了一遍。已修正，教训：涉及权限/隐私边界的默认行为，要按“最保守的解释”写，而不是按“最方便的解释”。
