# P3 开发经验（2026-11-19）

## 成功的方案及原因
1. **权限检查写成纯函数 check()，与执行 execute() 分离**：check() 只读配置和注册表，不碰数据库、不调工具。成功原因：权限逻辑可以单独想清楚、单独测试；测试 3（只改配置改权限）直接测的就是 check() 的行为，不用跑完整执行链。
2. **拒绝发生在执行前，且用“数据库还在”证明**：测试 2 里 delete_file 被拒绝后断言 data/jarvis.db 仍在。成功原因：权限的正确性不能只看返回 denied，要看“真的没执行”；用副作用的缺席做断言，比看返回值更硬。
3. **先验证 unshare 可用，再写 sandbox.py**：动手前在命令行跑了 `unshare -n true` 和命名空间内外连 8.8.8.8:53 的对比（101 vs 0），确认真断网可行才写代码。成功原因：沙箱演练的价值全在“断网是真的”；如果 unshare 不可用，写再多代码也是自欺欺人。
4. **审计只记 hash，不记原文**：成功原因：工具参数可能含敏感内容，审计日志是长期保存的，记原文等于把敏感内容写进另一个地方。代价是排查不方便，留 P4 定是否加脱敏摘要。
5. **两层防线各司其职**：测试 5 证明网关管“能不能调工具”，gate 管“内容能不能进记忆”。成功原因：权限和内容治理是两个不同的问题，混在一起会互相掩盖——网关放行不等于内容可信，gate 拦截也不等于工具被禁。

## 下一轮开发计划（P4 规划器）
- Planner：任务分解（目标 → 步骤），每步绑定一个已注册工具 + 参数，步骤按顺序经网关执行。
- 任务追踪：每步状态 pending / running / done / failed / denied，失败一步即停，不继续往下走。
- 验收：一个三步任务（召回记忆 → 路由问答 → 写记忆）全程经网关，审计链完整；其中一步被拒绝时任务停下并报告，不绕过网关；任务可重跑，重跑结果一致。
- 预算：$0，不接真实 API。开始前仍需用户确认 P4 开始。
- 另外：P4 时定审计脱敏摘要字段，网关 actor 区分用户与规划器。
