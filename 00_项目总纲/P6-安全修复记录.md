### 2026-11-22 缺口修复轮续修（主代理，修复轮子代理 22/26 之后）

- 背景：修复轮子代理 08:20 交出 22/26（escape_1/2/3/5 未修），主代理接手续修沙箱命名空间 4 缺口。约束不变：不手工跑 unshare/mount 逃逸探测，只凭代码 + Linux 挂载语义设计修复、只用 pytest（已授权的验证路径）验证；文件读写与 `cat /proc/mounts`、`ls` 属诊断，不碰逃逸路径。
- 修法（sandbox.py，jarvis-p6-fix 内）：
  - 工程拷贝隔离：run_sandboxed 在 unshare 前把 base_dir 拷到 `tempfile.mkdtemp` 下的一次性目录，把拷贝 bind 到真实路径后 remount 只读；即使命名空间内把绑定 remount 成 rw，写操作也只落到拷贝上；拷贝目录在 finally 里删掉，失败时闭环返回 unsupported。
  - PID 命名空间：unshare 加 `-p --fork`（原只有 `-rnm`），沙箱进程成为新 PID 命名空间的 1 号进程；`_scrub_env` 另过滤含 `TRACE_CONTEXT` 的环境变量（实测 `JARVIS_TRACE_CONTEXT` 在 shell 环境里存在，04:10 经 /proc 泄露过，绝不进沙箱）。
  - 顶层目录：根 `/` 是 overlayfs 挂载点，子用户命名空间里无法 bind/remount（实测报错）；无锁定子挂载点的目录（/usr、/boot、/root、/srv、/media）逐个 bind 后 remount 只读；含锁定子挂载点的目录改盖 tmpfs——/opt、/var、/run（沙箱命令不需要），/var 盖掉后先 `mkdir -p /var/tmp` 再盖 /var/tmp；/tmp、/var/tmp、/mnt 仍按原设计处理。
  - /proc：挂载新的 proc 被拒绝（`mount: /proc: permission denied`），故直接盖空 tmpfs——沙箱内看不到任何进程（含自己的），/proc 彻底隐藏；escape_2 的计数因此为 0。
  - /etc 与 /home 是残留缺口（见下）：/etc 保持原样（沙箱命令要读 /etc/passwd 等），/home 是真实工程目录的祖先、盖掉会遮住工程路径故跳过；/dev、/sys 保持原样（要读 /dev/null、/dev/urandom；sysfs 本就基本只读）。
- 修复过程的实测规律（均只由 pytest 重跑验证）：

### 关键发现与坑（本轮实测，非推断）

- 普通 remount 在本环境失败：`mount -o remount,ro /etc` 报“mount point not mounted or bad option”（exit 40），/home 同理（exit 47）。bind 形式的 remount 可行：/etc 用自 bind（`mount --bind /etc /etc` 再 `mount -o remount,ro,bind /etc`），/dev 用 --rbind（设备 bind 是子挂载，非递归 bind 会藏掉它们），/home 用 --rbind。退出码表新增 20（make-rprivate）、201–203（manager 自身失败）。
- supervisor 方案被实测推翻（任务原建议）：命名空间内 init（sandbox_supervisor.py）以同一信号自杀，三次实测全活下来——SIGTERM 自杀 → 外层 143（=128+15），SIGKILL 自杀 → 137（=128+9），SIGSEGV → 139（=128+11），全部走到 `return 128 + sig`。原因：命名空间 init 是 SIGNAL_UNKILLABLE，从命名空间内部发的信号（即使 SIGKILL，handler 为 SIG_DFL）会被内核忽略；只有来自祖先命名空间（或内核）的 SIGKILL/SIGSTOP 才能杀死它。结论：命名空间内的任何进程都无法以“死于信号”把信号传出，PID 1 只能正常退出。supervisor 文件已删除，改用 `sandbox_manager.py`。
- manager 设计（取代 `unshare` 命令行）：管理器是宿主侧普通进程（不是 init），用 ctypes 调 unshare() 建命名空间，fork 子进程，子进程再 fork 孙进程（命名空间 init，sh 跑 setup 脚本、exec 命令）；管理器等子进程、子进程等孙进程，孙进程死于信号时逐级以同一信号自杀，subprocess.run 看到真正的负 returncode（非合成）。挂载传播改由 setup 脚本第一步 `mount --make-rprivate /`（等价于 unshare 命令行的默认 private 设置，否则沙箱内挂载回传宿主）。
- id-map 必须由父进程写（实测 EPERM）：子进程 unshare 后自己写 /proc/self/uid_map "0 0 1" 报 EPERM（202）。本环境是容器，进程的 root（uid 0）只是容器用户命名空间里的 root，在父命名空间里对应一个普通 uid；自己写时外层 uid 0 不是自己的父命名空间 euid，单行自映射与 CAP_SETUID 检查都不通过。正确做法是 `unshare -r` 的做法：父进程写子进程的 /proc/<pid>/uid_map。子进程 unshare 后经管道发 ready，父进程写完映射（setgroups deny → uid_map → gid_map）再发 done，子进程收到才继续。
- PID 1 的信号语义（本轮三次实测确认，测试期望据此定）：(a) 自发 SIGTERM/SIGKILL：PID 1 忽略，命令正常退出 0——test_p6_fix2.py 里这两项已改为文档化行为测试，不再断言负 returncode；(b) SIGXCPU（CPU 软上限）：PID 1 同样忽略（SIG_DFL），忙循环跑到硬上限才由内核发 SIGKILL 杀死——沙箱外对照：同一 busy loop、同样的 RLIMIT_CPU(2,3) 在沙箱外死于 SIGXCPU（-24，2.04s），沙箱内死于 SIGKILL（-9）；resource_3 的断言已据此改为 returncode<0 + "signal 9"（原先断言的 "signal 24" 是错的）；(c) SIGSEGV 真实崩溃（ctypes 读空指针）：同步 fault 能杀死 PID 1，返回负 returncode——这是信号致死的第二项证明。
- escape_6 触发方式已改（行为有意变更）：原来传清空 PATH 的 env 让 which('unshare') 返回 None；fix2 起 run_sandboxed 不用 unshare 命令行（ctypes + 绝对路径的 sys.executable），PATH="" 已无法让沙箱不可用。改用不存在的工程目录触发 fail-closed（拷贝失败 → unsupported），并加断言命令标记 "should-not-run" 未出现在任何输出里（证明命令确实没跑）。
