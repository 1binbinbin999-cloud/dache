## 5. 版本回滚方法

### 代码版本回滚
- 每轮一个完整目录，上一轮目录原样保留。回滚 = 直接用上一轮目录：
```bash
# 例如从 P5 回到 P4
cd ~/workspace/Jarvis/04_源代码/jarvis-p4
python3 jarvis.py boot   # 验证上一轮仍能启动
```
- 整个工程回滚：复制整个 `~/workspace/Jarvis/` 目录即可恢复（见 `09_版本记录/版本记录.md`，v0.0.0 为基线回滚点）。

### 单次改动回滚（P5 流程内）
```bash
cd ~/workspace/Jarvis/04_源代码/jarvis-p5
python3 jarvis.py improve-rollback --id imp-xxx   # 用 data/backups/ 里的备份恢复原文件
```
- 部署时备份在 `data/backups/<提案id>-<文件名>`；二次回滚被拒绝（already rolled back）。

### 数据回滚
- 记忆修正回滚：`python3 jarvis.py memory-rollback --correction-id corr-xxx`（旧事实恢复 verified，新事实标 superseded，反向 Correction 记录保留）。
- 记忆库导出/导入：`memory-export --out data/memory-export.jsonl` / `memory-import --in data/memory-export.jsonl`（按 id 幂等，重复导入不重复）。

## 7. 数据权威关系（修订新增，2026-11-19）

第一阶段有三类持久化数据，权威性不同，不得混用。以下定义以 P0–P5 的实际代码为准，不是理想设计。

### 7.1 三类数据的权威性

| 数据 | 位置 | 权威内容 | 不权威的内容 |
|---|---|---|---|
| JSONL 事件日志 | 各版本目录 `data/events.jsonl` | **“何时发生了什么”的唯一事实源**：boot、工具调用、路由调用、提案、部署、回滚等事件的发生顺序与结果（含结果 hash、审计字段） | 事件的**内容原文**：审计只记 hash 与参数键名摘要，不记参数值与记忆文本，无法从日志还原原文 |
| SQLite 记忆与任务数据 | 各版本目录 `data/jarvis.db` | **当前状态的唯一事实源**：记忆事实的当前文本与状态、任务与计划的当前状态、种子任务 | 历史：已被 superseded/expired 的旧判断只在库内留痕，当前状态不代表历史；事件的发生顺序以日志为准，不以库为准 |
| improvements.db 治理记录 | 仅 jarvis-p5 `data/improvements.db` | **自我改进治理的唯一事实源**：提案、评价、部署记录的状态机（proposed → evaluated → approved → deployed / rolled_back） | 部署的实际文件内容：部署是否生效以目标文件本身为准，不以部署表为准 |

### 7.2 重建关系

- **从 jarvis.db 重建事件日志**：不可行。库内没有事件的发生顺序与审计字段，丢了日志就丢了“何时发生”的证据，只能从库的当前状态反推“现在是什么”，不能反推“怎么变成现在这样的”。
- **从事件日志重建 jarvis.db**：不可行。日志不含记忆文本与参数值（只有 hash），无法还原事实内容。日志能证明“某次调用发生过、结果 hash 是什么”，不能恢复数据本身。
- **从 improvements.db 重建部署**：不可行。部署表只记“部署过、备份在哪”，不含文件内容；真正能恢复文件的是 `data/backups/` 里的备份文件。
- **结论**：三类数据互相不能完整重建，必须各自备份。导出 = 复制整个版本目录（含三类数据与备份目录），只导其中一类不算完整导出。

### 7.3 冲突处理规则

| 冲突情形 | 处理规则 |
|---|---|
| 日志说某次 memory-add 被隔离，库里却有这条事实且状态为 verified | 以日志为准报不一致：该事实的来源可疑，标记待人工复核，**不得自动改库**，不得自动删日志 |
| 库里事实状态为 superseded，但 corrections 表无对应 Correction 记录 | 以库为准报不一致：修正流程有缺口，标记待人工复核，**不得自动补写** Correction 记录 |
| improvements.db 说某提案已 deployed，但目标文件不含该改动 | 以目标文件为准报不一致：部署未生效或已被外部改动，标记待人工复核，**不得自动重部署** |
| improvements.db 说某提案已 rolled_back，但目标文件仍含该改动 | 以目标文件为准报不一致：回滚未生效，标记待人工复核，**不得自动再回滚一次**（二次回滚本身被拒绝，见 P5 测试 5） |
| `data/backups/` 里无对应备份文件，但部署表说已部署 | 回滚不可行，报不一致并标记为高风险：该部署无回滚路径，后续改动前必须先恢复备份机制 |
| 三类数据时间戳互相矛盾（如部署时间早于提案时间） | 以最早的可信记录为准报不一致，标记待人工复核 |

总原则：**冲突只报告、不自动修复**。自动修复会制造第二份“真相”，与“事件日志是唯一事实源”冲突。人工复核前，系统以“报不一致、停下相关操作”为默认行为。

### 7.4 数据不一致恢复测试设计（只设计，不实现——本次不改代码）

以下测试在第二阶段实现（需用户批准后才写代码），测试目标是“系统在数据不一致时能发现、能报告、不乱改”。

| 编号 | 测试 | 操作 | 预期结果 |
|---|---|---|---|
| REC-01 | 日志丢失 | 删 `data/events.jsonl` 后 boot | boot 成功（数据库 intact）；健康检查报告审计日志缺失，不静默重建假日志 |
| REC-02 | 日志与库冲突 | 手工把一条已隔离事实的库状态改为 verified 后跑一致性检查 | 检查报告不一致，指明事件与库记录，不自动改库 |
| REC-03 | 修正记录缺失 | 手工删一条 Correction 记录后跑一致性检查 | 检查报告不一致，指明 superseded 事实无对应修正记录，不自动补写 |
| REC-04 | 治理库丢失 | 删 `data/improvements.db` 后查 improve-status | 提案查不到，报 not_found；`data/backups/` 备份文件仍在，回滚仍可凭备份文件手工恢复，但治理历史已丢，须在报告中写明 |
| REC-05 | 备份丢失 | 删 `data/backups/` 里某次部署的备份后跑 improve-rollback | 回滚明确失败并报错，不静默成功、不写假状态 |
| REC-06 | 部署与文件不一致 | 部署后手工改回目标文件，再查 improve-status | 报告部署状态与文件内容不一致，不自动重部署 |
| REC-07 | 导出完整性 | 导出整个版本目录，在新位置恢复后逐项核对三类数据 | 三类数据齐全且一致；缺任何一类即报告导出不完整 |

> 实现说明：REC-02、REC-03、REC-06 需要一个新的一致性检查命令（例如 `jarvis.py consistency-check`），第一阶段没有这个命令。本次只做测试设计，不写代码；实现排在第二阶段 S2-4（遗留问题处理）中，需用户批准。
