## P0：离线启动原型（第一轮）

### 本轮开发目标
证明 Agent Core 是确定性程序，不依赖任何外部 AI 模型和网络，能启动、读自己的数据、跑本地任务。

### 技术方案
- 语言：Python 3.12（云端已装；如用户要求 TypeScript，在 P0 前改，成本最低）。
- 结构（04_源代码/jarvis-p0/，确认后才创建）：
  - `jarvis.py`：CLI 入口，只做 `boot`、`health`、`list-tasks` 三个命令。
  - `core/`：确定性编排器，状态机 + 事件日志（JSONL 追加写），不导入任何模型 SDK。
  - `config/config.yaml`：配置，不含密钥；模型配置只留占位，不填真实 Key。
  - `data/`：SQLite 文件 + 种子数据（合成任务 5 条，绝不用真实私人数据）。
- 启动路径：配置 → 数据库 → 权限表 → 审计日志 → 调度器，先启动，模型后加载（P0 根本不加载模型）。
- 不做：不装 Ollama，不调任何 API，不做记忆提取，不做 Planner。

### 实际交付内容
- 可运行代码 + `README.md`（怎么跑、怎么停、怎么看日志）。
- `05_测试记录/P0-测试记录.md`：测试用例与结果。
- `06_问题与修复/P0-问题记录.md`：遇到的问题、根因、修复。

### 运行和测试结果（待 P0 执行后填写）
- 测试 1：正常启动，`jarvis boot` 成功，健康检查通过。
- 测试 2：拔网模拟（无外部 Key、断开模型配置），仍能启动、读种子任务、列出待办。
- 测试 3：重复启动、异常退出后重启，事件日志不丢、不重复执行已完成任务（幂等抽查）。
- 测试 4：导出测试：复制整个 `Jarvis/` 到新目录，仍能启动（证明不绑定 Muse 专属路径）。

### 存在的问题（待填写）
- 待 P0 实测后记录。

### 验收标准（全部通过才算 P0 通过）
1. 无任何 API Key、无网络时，`jarvis boot` 成功，健康检查通过。
2. 能读本地 SQLite 种子数据，列出 5 条任务。
3. 事件日志追加写，含时间、事件、结果；重启后日志不丢。
4. 复制目录到新位置仍能启动。
5. 代码中无任何模型供应商 SDK 的 import（grep 可验证）。

### 下一步计划
P0 通过后进入 P1；不通过则修到通过，不跳轮。

## P1：记忆治理原型

### 本轮开发目标
证明记忆不是“存聊天记录”，而是能写对、改对、过期能被取代，错误不污染后续推理。

### 技术方案
- 在 P0 事实库上加表：`memory_facts(id, type, text, confidence, evidence_grade, source, created_at, valid_from, valid_until, status, superseded_by)`，type ∈ {事实/观点/推断/待验证}，status ∈ {verified/provisional/superseded/disputed/expired}。
- 写时 gate：新事实写入前做一致性检查，低于阈值进隔离区，不直接入库；高置信度变更需复核标记。
- 提取：P1 先用规则 + 模板提取（不调 LLM），证明流程本身成立；LLM 提取留到 P2 路由就绪后再接，避免一开始就把记忆正确性押在模型上。
- 检索：SQLite 全文 + 简单向量占位（先不引入向量库，P1 只验证治理流程）。

### 实际交付内容
- 记忆写入/召回/修正代码 + 测试数据（100 条合成对话，绝不用真实对话）。
- 测试：过期事实被标 superseded，不被当成当前事实召回；注入 10 条假事实，拦截 ≥8 条；给画像一条错误推断，再给 3 条反证，生成 Correction 记录，旧判断保留历史。

### 验收标准
1. 过期事实不被当成当前事实召回。
2. 注入测试拦截 ≥8/10。
3. 修正生成 Correction 记录，旧判断可查、用户可一键改回。
4. 记忆库可导出为 JSONL，含 schema 版本号，换环境可导入。

### 预算
$0，不调付费 API。

## P2：路由切换原型

### 本轮开发目标
证明换模型只改配置，Core、Memory、Policy、Audit、工具、数据全部不动。

### 技术方案
- Model Router：逻辑模型名 `fast/capable/reasoning/local/embedding`，映射表在配置文件，不进业务代码。
- 先用 Stub（本地假模型，返回固定格式）+ LiteLLM 配置占位，验证切换链：首选 → 备选 → 本地。
- 待用户决定首批接入哪两家供应商后，才实际接通 1–2 家真实 API，且单项测试 ≤$5。

### 验收标准
1. 同一任务在 Stub A → Stub B 间切换，只改配置，输出格式与 Audit 一致。
2. 任一环节超时/失败即切换，不死循环重试。
3. 每次调用记模型、token、成本、耗时、结果 hash（Stub 时 token/成本记 0 并标注）。
4. 无 Key 时直接走降级，不报错瘫痪。

## P3：工具网关原型

### 本轮开发目标
证明工具调用受权限控制，提示注入不能调动删改工具。

### 技术方案
- 1 个读工具（读指定目录下的文件）+ 1 个写工具（写笔记到指定目录）。
- 能力卡 + allowlist + 参数 Schema + 业务校验（路径在白名单内）。
- 审批分级：读 L0 自动，写 L1 确认（P3 先用命令行确认，后续再接人工审批界面）。
- 沙箱：P3 先用进程级隔离 + 只读挂载思路记录，Docker/gVisor 待实体机评估；云端无 Docker，不硬装。
- 审计：每次调用记时间、调用者、工具、参数 hash、策略判定、结果摘要。

### 验收标准
1. 注入指令（在工具返回/文件内容里藏“删除所有文件”）调删工具时，被代码层拒绝，Audit 有记录。
2. 超出白名单路径的调用被拒绝。
3. 写工具需确认，未确认不执行，超时作废。
