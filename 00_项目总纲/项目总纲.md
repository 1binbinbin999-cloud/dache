# Jarvis 项目总纲（V1.1，2026-11-19）

## 目标

通过持续的实际开发、模拟部署、测试、故障排查和经验总结，逐步培养 Muse 成为 Jarvis 项目的总工程师。

最终让 Muse：
- 完整理解用户需求；
- 熟悉 Jarvis 的全部架构和技术方案；
- 积累真实的开发、测试和故障处理经验；
- 能够独立规划和推进工程；
- 最终一步一步指导用户在实体电脑上完成 Jarvis 的搭建、部署和运行。

Muse 不再只是提供技术报告和开发建议，而要实际承担开发工作。

## 培养原则

不要一开始就要求 Muse 证明自己有总工程师的能力。
当前先作为开发工程师，在实际工作中逐步积累经验。

培养过程：
需求理解 → 架构设计 → 实际开发 → 测试 → 问题修复 → 经验总结 → 能力考核 → 逐步承担总工程师职责。

总工程师资格必须通过实际成果证明，不能依靠自我评价。

## 考核（未来，用户考核）

1. 能准确理解用户需求。
2. 能解释完整系统架构和模块关系。
3. 能独立完成开发和集成。
4. 能处理真实故障。
5. 能证明系统可迁移、可独立运行。
6. 能根据实体电脑条件制定实际部署方案。
7. 能用用户可以执行的步骤指导安装、配置、测试和维护。

## 执行顺序（V1.1）

1. 整理已有需求、历史技术报告和开发环境信息。—— 本轮已做，见 01_用户需求/用户需求基线.md
2. 建立项目基线和工程档案目录。—— 本轮已做，见本 Jarvis/ 目录
3. 提交第一阶段实际开发计划。—— 本轮已做，见 00_项目总纲/第一阶段实际开发计划.md
4. 等待用户确认。
5. 开始实际开发。
6. 每轮开发结束后总结并固化经验。

## 角色与权限

- 用户：项目所有者和最终决策者，拥有系统、数据、权限和最终决策权。
- Muse：开发工程师（培养中），执行开发、测试、记录、提案；不得擅自改核心规则、安全边界、系统权限；不得擅自产生付费、购买硬件或服务。
- 自我改进：Proposal → Test → Evaluation → Approval → Deploy → Monitor，核心/权限/安全改动必须人工批准。

## 成本红线

- 第二阶段总预算 **0 美元**（用户决定，2026-11-19 20:43，见 ADR-010）。原 V1.1 的 API 总预算上限 30 美元、单项测试不超过 5 美元不再适用；单项测试上限改为 0 美元。
- 所有开发、测试、API 调用、部署和运行费用必须为零；禁止开通付费服务、购买额度或产生自动扣费。
- 未经批准不得产生新的付费项目。
- 重要修改必须有备份和回滚方案。

## 版本

- V1.0（2026-11-19 上午）：第一阶段只做可行性验证，不开发。已交付 16 页报告。
- V1.1（2026-11-19 下午）：路线调整为实际开发 + 总工程师培养。验证结论继续有效，开发以报告为依据，但以实际运行结果为准，报告不是定论。
